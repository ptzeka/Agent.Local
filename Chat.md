Here's the full map of the React chat over the CLI session. It spans three processes: browser (web) → host BFF → agent server, with the browser never talking to the agent directly — the cookie stays at the host, and the agent only ever sees OBO/service bearers.

Map: open chat
Click — the chat icon on a work row (workflow.tsx:411) sets chatWork, which mounts WorkChatDialog. The button is disabled unless the work has a workspace and isn't terminal.
Provision — on mount, the dialog's effect calls api.provisionSession(workId) (WorkChatDialog.tsx:82) → PUT /api/agent/cli/:workId (agentCliApi.ts:26). The host (agent-cli.ts:18) gates on workflow:write + work ownership, rejects locked/no-workspace works, then calls the agent's POST /session/create under its own service token, passing the cached CLI sessionId if one is stored. The agent (session-api.ts:19) requires agent:trigger, reuses the cached session when still valid or mints a fresh one (persisting a new transcript only for a brand-new id), and the host upserts the result on (work_id, kind='cli').
Stream attach — the dialog opens new EventSource(streamUrl, {withCredentials:true}) (cookie auth is load-bearing: EventSource can't set headers). The host's GET /api/agent/cli/:workId (agent-cli.ts:44) exchanges the user's access token for an OBO bearer (sub=user, act=host) and fetches the agent's GET /ssereceive/:sessionId (sender.ts:104), then pipes the SSE bytes verbatim to the browser with backpressure.
Runtime build — the agent's SseReceiver 403s unless the OBO subject matches the session's bound owner, evicts and drains any stale connection ("newest tab wins"), then builds a per-connection runtime resumed off the session (passing the verified bearer so the session is stamped with the real user — the piece we added yesterday), registers it in SseQueue, and emits the ready frame. The dialog flips ready=true and enables the input.
Map: send and get response
Send — Enter/Send appends the user bubble optimistically and POST /api/agent/cli/:workId/input (WorkChatDialog.tsx:122). Host re-checks ownership/lock, then posts to the agent's /receive with a fresh runId per turn and the sessionId in the x-session-id header (sender.ts:121).
Route to the live runtime — HttpReceiver is pure transport: validates, stamps provenance, publishes EXECUTION_REQUESTED. ExecutionRunner.run sees the session has a live SSE connection in SseQueue and calls live.runtime.injectInput(input, "user") — no new runtime, no webhook; the same runtime built at attach handles the turn. (No live connection → it'd be a one-shot job with a result envelope instead.)
Response streams back — the SSE receiver projects the runtime's event bus to chat frames (ssereceiver.ts:90): turn {start} (dialog shows Stop/busy), delta per token (appended verbatim to the open streaming bubble — the state machine at WorkChatDialog.tsx:48), then end closes the bubble; a non-streaming model instead gets one message frame with full content. turn {done} clears busy and belt-and-suspenders-closes the bubble. A 15s : keep-alive comment keeps proxies from dropping the idle stream.
Stop — the Stop button → /stop → host → agent /session/interrupt → EXECUTION_INTERRUPT on the bus → runner calls runtime.stopAllWork() on the live runtime only. Session and stream stay up; the response is 202 either way.
Map: close
Dialog close — onClose unmounts the dialog; the effect cleanup sets cancelled (dropping a provision that resolves late) and calls source.close() (WorkChatDialog.tsx:111). Transcript state is local, so reopening starts with an empty pane but the same agent session (the transcript persists server-side).
Host teardown — the browser disconnect fires the host response's close, which aborts the upstream fetch to the agent (agent-cli.ts:77); the aborted stream is treated as a normal end, not an error.
Agent teardown — the agent request's close handler (ssereceiver.ts:123) clears the heartbeat, unsubscribes, deregisters from SseQueue, stops the turn loop, and drains the runtime (flush session to disk, close MCP clients) with a 10s timeout. The session row stays resumable — the next open re-provisions and resumes the same transcript.
Safety nets — if the disconnect never propagates (dead tab, dropped proxy), either the next attach evicts the stale connection, or the runner's heartbeat sweep (runner.ts:66) reaps any connection whose response is no longer writable. session/close (host Stop/pause of the work, not the chat) additionally cancels in-flight runs and marks the session done.
One asymmetry worth knowing: provision and input ride the host's plain service token (the agent never learns the user on those paths — ownership was gated host-side), while the SSE stream rides the OBO user token and is the only agent-side user check. That's by design per the comments, but it means the trust anchor for "whose session is this" is the host's works.userId check plus the stream binding — /receive with a valid service token and a known sessionId would accept input from any service holding agent:trigger.

does the STOP spinner listen to specific events
Yes — it's driven entirely by the turn SSE frames, not by the Stop click itself.

The chain:

UI: busy flips on exactly one listener — WorkChatDialog.tsx:91-95: source.addEventListener("turn", ...) sets busy = (status === "start"). When busy is true the Send button is replaced by the Stop button with the CircularProgress spinner inside it (WorkChatDialog.tsx:197-199). Nothing else touches busy — not the send click, not the stop click, not deltas.

Agent: those frames come from the turn loop's lifecycle callback in ssereceiver.ts:108-113 — turn-start → write("turn", {status:"start"}), and turn-done → {status:"done"} but only when !turnRunner.isBusy, i.e. no further queued input is about to start another turn (so rapid-fire inputs don't blink the spinner off between turns).

Two consequences of that design:

Sending doesn't show the spinner immediately. There's a round trip — POST /input → host → agent /receive → bus → injectInput → turn loop wakes → turn-start frame comes back — before busy flips. For a beat after hitting Enter, the Send button is still visible (though busy-guarded send() isn't the gate; the empty draft is).
Pressing Stop doesn't stop the spinner. The click just fires /stop → /session/interrupt → EXECUTION_INTERRUPT → runtime.stopAllWork(). The spinner only clears when the interrupted turn actually winds down and the loop emits turn-done. That's honest UX (spinning until the agent has really stopped), but if stopAllWork() ever hangs or the interrupt is lost, the spinner spins forever with no timeout — the only escape is closing/reopening the dialog, which rebuilds the stream and state.
Also worth noting: busy/spinner state is per-connection and not replayed. If the stream reconnects (EventSource auto-reconnect) or you reopen the dialog mid-turn, no turn {start} is re-emitted for the already-running turn — the runtime is rebuilt on attach, so in practice the old turn died with the old connection anyway; you'll never see a stale spinner, but you also won't see the tail of a turn that was in flight when the stream dropped.
